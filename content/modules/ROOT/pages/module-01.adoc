= Prepare Production Configuration

Your LAMP application works great in development with volume mounts. Now transform it for production - files baked into the image, packaged as a bootable VM.

In this module, you'll review the application files and create the systemd service that initializes the database on first boot.

*Time: ~8 minutes*

== Understand the Production Workflow Difference

In Lab 1, you used **volume mounts**:
- Files lived on your host
- Container accessed them via mount
- Edit anytime, changes appeared instantly
- Mutable (great for development)

In Lab 2, you'll use **COPY directives**:
- Files baked into the image at build time
- No volume mounts, no host access
- Can't edit after build (immutable)
- Perfect for production

Same application, different workflow. The production Containerfile will `COPY` these files instead of mounting them.

== Create the Database Initialization Service

In development, you manually initialized MariaDB. In production, the database needs to initialize automatically on first boot.

Create a systemd service that runs once:

[source,bash,role=execute]
----
cat > ~/lamp-bootc/mariadb-setup.service << 'EOF'
[Unit]
Description=MariaDB Database Initialization
After=mariadb.service
Requires=mariadb.service

[Service]
Type=oneshot
ExecStart=/usr/bin/mariadb -u root < /var/local/setup.sql
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
EOF
----

This service:
- Runs after MariaDB starts (`After=mariadb.service`)
- Executes the SQL script once (`Type=oneshot`)
- Won't run again on subsequent boots (`RemainAfterExit=yes`)
- Runs automatically on boot (`WantedBy=multi-user.target`)

Verify the service file was created:

[source,bash,role=execute]
----
cat ~/lamp-bootc/mariadb-setup.service
----

== Understand the Production Image Structure

Your production Containerfile will:

1. Start from `rhel-bootc:10.1` (bootable base, not ubi-init)
2. Install the LAMP stack (MariaDB, Apache, PHP)
3. **COPY** application files into the image (not volume mount)
4. **COPY** the systemd service into the image
5. Enable all services to start on boot
6. Configure SELinux and firewall

The key difference from Lab 1: files are **inside the image**, not mounted from outside.

This makes the image:
- Immutable (can't edit files after build)
- Reproducible (every deployment is identical)
- Portable (entire app packaged in one artifact)
- Versionable (tag the image, deploy specific versions)
