= Deploy and Validate the Bootable Application

*Lab 2 of 2, Module 3*

[.lead]
**Goal:** Boot the disk image as a VM, prove the LAMP stack comes up on its own, then enable the Showroom LAMP Application tab.

This is the pay-off for Lab 2: **boot once, serve the app** — no manual post-boot setup.

*Time: ~10 minutes*

[IMPORTANT]
====
**Prerequisite:** Module 2 must be complete. `~/lamp-bootc/output/qcow2/disk.qcow2` must exist. If it does not, finish Module 2 first (disk build can take 10–15 minutes).
====

== Copy the Disk Image to Libvirt Storage

Move the disk image into libvirt's default pool:

[source,bash,role=execute]
----
sudo cp ~/lamp-bootc/output/qcow2/disk.qcow2 /var/lib/libvirt/images/lamp-vm.qcow2
----

Set ownership:

[source,bash,role=execute]
----
sudo chown qemu:qemu /var/lib/libvirt/images/lamp-vm.qcow2
----

The disk image is now ready for VM creation.

== Create and Start the Virtual Machine

Define the VM and import the disk:

[source,bash,role=execute]
----
sudo virt-install --name lamp-vm \
  --disk /var/lib/libvirt/images/lamp-vm.qcow2 \
  --import \
  --memory 2048 \
  --vcpus 2 \
  --os-variant rhel10-unknown \
  --graphics none \
  --noautoconsole
----

This creates a VM with:
- 2 GB RAM
- 2 vCPUs
- The bootable disk you created

Start the VM:

[source,bash,role=execute]
----
sudo virsh start lamp-vm
----

Wait ~30 seconds for the VM to boot:

[source,bash,role=execute]
----
sleep 30
----

Check the VM is running:

[source,bash,role=execute]
----
sudo virsh list
----

*Expected output:*

----
 Id   Name      State
--------------------------
 1    lamp-vm   running
----

Your bootable LAMP application is now running as a VM.

== Get the VM's IP Address

Find the VM's IP address:

[source,bash,role=execute]
----
sudo virsh domifaddr lamp-vm
----

*Expected output:*

----
 Name       MAC address          Protocol     Address
-------------------------------------------------------------------------------
 vnet0      52:54:00:xx:xx:xx    ipv4         192.168.122.XXX/24
----

Note the IP address (192.168.122.XXX). You'll use it to access the application.

Export it as a variable for easier testing:

[source,bash,role=execute]
----
VM_IP=$(sudo virsh domifaddr lamp-vm | grep ipv4 | awk '{print $4}' | cut -d'/' -f1)
echo "VM IP: $VM_IP"
----

[NOTE]
====
`~/.lamp-vm-ip` only exists if you used the Module 3 **solve** button. If that file is missing, use the `virsh domifaddr` command above - that is the supported path for manual steps.
====

== SSH into the VM

Connect to the VM:

[source,bash,role=execute]
----
ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null core@$VM_IP
----

When prompted, enter the password: `redhat`

[NOTE]
====
The SSH options (`-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null`) bypass host key verification. This is appropriate for lab VMs that get rebuilt with new SSH keys but reuse the same IP address. In production environments, you would verify host keys for security.
====

You're now inside the bootable VM. This is a complete RHEL system that booted from your image.

== Verify Services Started Automatically

Check MariaDB is running:

[source,bash,role=execute]
----
systemctl status mariadb --no-pager
----

*Expected output (key line):*

----
   Active: active (running) since...
----

Check Apache is running:

[source,bash,role=execute]
----
systemctl status httpd --no-pager
----

*Expected output (key line):*

----
   Active: active (running) since...
----

Check the database initialization service ran:

[source,bash,role=execute]
----
systemctl status mariadb-setup --no-pager
----

*Expected output (key lines):*

----
   Loaded: loaded (/etc/systemd/system/mariadb-setup.service; enabled)
   Active: active (exited) since...
----

`active (exited)` with `enabled` is correct for this oneshot service: it ran once at boot, initialized the database, and exited. It will not keep a long-running process.

== Verify the Database Initialized

Query the database:

[source,bash,role=execute]
----
mariadb -u hellouser -p'SecurePassword' hellodb -e "SELECT * FROM greetings;"
----

*Expected output:*

----
+----+-------------------------------------+---------------------+
| id | message                             | created_at          |
+----+-------------------------------------+---------------------+
|  1 | Hello, World!                       | YYYY-MM-DD HH:MM:SS |
|  2 | Welcome to LAMP with Image Mode!    | YYYY-MM-DD HH:MM:SS |
|  3 | This is a production bootable image!| YYYY-MM-DD HH:MM:SS |
+----+-------------------------------------+---------------------+
----

The database initialized automatically on first boot. The data is from your `db-setup.sql` file that was baked into the image.

== Test the Application from Inside the VM

Test the PHP application:

[source,bash,role=execute]
----
curl http://localhost
----

You'll see HTML output with your greeting messages. The full LAMP stack works - MariaDB → PHP → Apache all connected.

Exit the VM:

[source,bash,role=execute]
----
exit
----

You're back on your host.

== Test the Application from Your Host

You are back on the buildhost. The VM lives on a private libvirt network (`192.168.122.x`), so you cannot open `http://<VM_IP>` in your laptop browser. Validate the app from the terminal instead.

First, make sure `VM_IP` is still set in this shell (it can be lost if the terminal reconnects):

[source,bash,role=execute]
----
VM_IP=$(sudo virsh domifaddr lamp-vm | grep ipv4 | awk '{print $4}' | cut -d'/' -f1)
echo "VM IP: $VM_IP"
----

Test the application over the VM network:

[source,bash,role=execute]
----
curl -s http://$VM_IP | grep -A 1 "Hello, World"
----

*Expected output:*

----
<strong>Hello, World!</strong><br>
<small>Created: YYYY-MM-DD HH:MM:SS</small>
----

Confirm all three database messages are present:

[source,bash,role=execute]
----
curl -s http://$VM_IP | grep -E "Hello, World|Welcome to LAMP|production bootable"
----

*Expected output:*

----
<strong>Hello, World!</strong><br>
<strong>Welcome to LAMP with Image Mode!</strong><br>
<strong>This is a production bootable image!</strong><br>
----

The application is reachable from the buildhost. That proves Apache, PHP, and MariaDB are working end to end.

== Enable the LAMP Application Tab

Terminal `curl` already proved the app. The Showroom **LAMP Application** tab needs one more step because the VM sits on a private libvirt network.

image::lamp-tab-forwarder.svg[Diagram of Showroom tab to OpenShift route to buildhost socat forwarder to nested VM port 80,width=1000,align=center]

Run this on the **buildhost** (prompt must be `[rhel@buildhost ~]$`, not inside the VM), and only after `curl http://$VM_IP` succeeded:

[source,bash,role=execute]
----
sudo enable-lamp-webapp-forward
----

*Expected output (IP/PID will vary):*

----
VM IP: 192.168.122.101
Service state: active
LISTEN 0      5            0.0.0.0:8080      0.0.0.0:*    users:(("socat",pid=XXXXX,fd=5))
OK: LAMP app reachable via http://127.0.0.1:8080
Refresh the Showroom LAMP Application tab now.
----

Then refresh the **LAMP Application** tab. You should see the same greeting page.

[NOTE]
====
If the command is not found, the lab host was not set up from the current content. Re-provision, or ask a facilitator. Do not paste long multi-line socat/`dnf` blocks into the web terminal - that is what this helper replaces.

If the helper runs but fails:

[source,bash]
----
sudo systemctl status lamp-webapp-forward.service --no-pager
sudo journalctl -u lamp-webapp-forward.service -n 20 --no-pager
----
====

This is the production deployment. The VM booted with:
- Operating system configured
- Services started automatically
- Database initialized
- Application code deployed
- Firewall rules applied

No manual setup. No SSH-ing in to configure things. Just boot and run.

== Understand What You Built

You've completed the full application developer workflow with Image Mode:

**Lab 1 - Development workflow:**
- Volume mounts (`-v ~/lamp-dev/app:/app` in Lab 1)
- Mutable files (edit anytime, changes appear instantly)
- Fast iteration (no rebuild needed)
- Perfect for development

**Lab 2 - Production workflow:**
- COPY directives (files baked into image)
- Immutable deployment (can't edit after build)
- Bootable disk image (complete OS + application)
- Perfect for production

**Same application. Two workflows. Different trade-offs.**

The image you built is:
- **Immutable** - can't SSH in and change files
- **Reproducible** - every deployment is identical
- **Versionable** - tag the image, deploy specific versions
- **Portable** - runs anywhere you can boot a VM

This is different from other Image Mode labs:
- They build OS images with monitoring tools
- You built an application deployment artifact
- They focus on platform engineering
- You focused on application development

[TIP]
====
*What's next?*

In production, you'd:
1. Push the bootable image to a registry (like quay.io)
2. Deploy to multiple VMs (cloud, bare metal, edge)
3. Update by building a new image and rebooting VMs
4. Rollback by booting the previous image version

Image Mode gives you immutable infrastructure for applications, not just operating systems.
====

== Stop the VM (Optional)

If you're done testing, stop the VM:

[source,bash,role=execute]
----
sudo virsh shutdown lamp-vm
----

Wait a few seconds, then verify it stopped:

[source,bash,role=execute]
----
sudo virsh list --all
----

*Expected output:*

----
 Id   Name      State
--------------------------
 -    lamp-vm   shut off
----

To start it again:

[source,bash,role=execute]
----
sudo virsh start lamp-vm
----

The application will boot ready to serve traffic every time.

Congratulations! You've packaged and deployed a database-backed LAMP application as an immutable bootable image using RHEL Image Mode.
